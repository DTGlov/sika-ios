## Locked architectural decisions (carried in)

- **Reconcile → type='adjustment' + category_id=NULL.** Already done by
  Accounts T1's `AccountService.insertReconcileAdjustment`. ✓
- **Adjustments DO NOT fire mutation chain.** `reconcileAccountInline`
  inserts the row and recomputes balances — it never calls
  `fireTransactionLoggedHooks`. TODO comment in two places already
  flags the 9.5b unification. ✓
- **Three reconcile entry points.** All converge on `ReconcileAccountSheet`:
  1. Accounts T1 scale icon — wired pre-T3.
  2. Wizard Step 1 ReconcileLink — wired in T3.
  3. IBS "Reconcile this account" — wired in T3.
- **IBS three actions:** Cancel / Reconcile this account / Log anyway.
  Log anyway sets `forceOverdraftSave`, re-enters `performSave`, and
  surfaces an amber warning toast after the green "Logged" toast.
- **Adjustments cannot be edited.** Menu's Edit button suppressed when
  `row.type == .adjustment`.
- **Reconcile success toast:** "Reconciled to <amount>" via the existing
  ToastManager (from Accounts T1 — not "Balance updated" per the prompt;
  the existing copy reads more clearly, and the toast came pre-built).

## Divergences from the prompt

1. **Reused `ReconcileAccountSheet` + `AppState.reconcileAccountInline`
   instead of building `ReconcileSheetView` / `ReconcileSheetViewModel` /
   `AdjustmentDraft` / `TransactionService.insertAdjustment`.** The
   prompt's spec was written without knowledge of Accounts T1's existing
   reconcile path. The existing infrastructure already produces
   type=adjustment + category_id=NULL transactions and recomputes
   account balances — rebuilding it would be redundant. The 9.5b TODO
   (momentum unification) is already in `AccountService.insertReconcileAdjustment`
   + `AppState.reconcileAccountInline`.

2. **Success toast copy: "Reconciled to <amount>" not "Balance updated".**
   The pre-existing path uses the former. Behavior is identical (success
   confirmation); changing the copy here would diverge from the standalone
   scale-icon flow. Both entry points now read the same message.

3. **IBS sheet presented via `.sheet(item:)` not `.sheet(isPresented:)`.**
   `.sheet(isPresented:)` had a race where the context cleared before the
   sheet captured it. Item-based avoids that and is the idiomatic SwiftUI
   pattern when the sheet's data lives outside view state.

4. **Validation skipped in edit mode.** The prompt didn't address this,
   but a user editing yesterday's expense shouldn't see IBS — the row's
   debit already moved the balance, so validating it again would force
   them through the override flow for routine corrections.

5. **No `AdjustmentDraft` / `appendAdjustment` / `JSONDecoder.supabase`
   path added.** Accounts T1's payload encoder + service write the row
   correctly already; `reconcileAccountInline` calls
   `recomputeAccountBalances` afterwards, which folds the new row into
   `accountsBalances` and indirectly updates the Home + T1 lists on the
   next refresh.

## Notes

- The amber warning toast is a separate overlay from the milestone toast;
  both live on `AuthenticatedRootView`. They can technically race if the
  user crosses a milestone AND hits an overdraft on the same save, but
  the two overlays stack cleanly and animate independently.
- The wizard's IBS path is one-shot — `forceOverdraftSave` resets to
  false after the override save completes. If the user opens IBS, taps
  "Log anyway", and the network save fails, the flag still resets on
  the next entry to the failure branch (`performAdd`'s `catch` doesn't
  reset it but the next save call goes back through validateBalance).
  Acceptable: a retry just shows IBS again.
