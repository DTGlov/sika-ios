## Locked architectural decisions

- **Read-only in T1.** No add/edit wizard wiring in this PR. The 3-dot Edit item is a `#if DEBUG print(...)` no-op placeholder for T2.
- **Hard delete with confirmation alert.** No undo. Mirrors web (no soft-delete column on the schema).
- **Page-50 + manual "Load more"** (NOT infinite scroll). Matches web.
- **Filter state in @Observable AppState.** Survives tab switches; resets on cold launch. Search is component-local `@State` (matches web's reload-loses-search behavior).
- **Period default: cycle** (current cycle from `profile.cycle_start_day`).
- **Sort default: `date-desc`.**
- **Bucket filter is client-side.** All other filters are server-side via PostgREST.
- **Day grouping is client-side** after fetch, by `transaction_date` string. Day order respects the date sort direction.
- **Tap on row: NO-OP** — web has no transaction detail view; never building one.
- **Pull-to-refresh added** (idiomatic iOS enhancement, not on web).
- **Server-side `account` filter covers both `account_id` AND `from_account_id`** via `or("account_id.eq.X,from_account_id.eq.X")` — matches web's intent applied to iOS columns.

## Adaptations from the prompt's blueprint

The prompt's blueprint assumed several things about iOS that weren't true. All flagged before grinding; adapted as follows:

1. **`to_account_id` does NOT exist on iOS Transaction.** iOS uses `account_id` (destination/main) + `from_account_id` (source for transfers). The web blueprint assumes `to_account_id` columns + `account = source / to_account = destination` convention. iOS schema is the inverse: `account_id` is destination, `from_account_id` is source. Same display intent ("source → destination"), different column names. The join uses `from_account:accounts!from_account_id(...)` and the title row reads `fromAccount.name → account.name`. The "filter by account" predicate covers both columns.
2. **`Transaction` model is NOT extended.** Adding optional joined fields (`category: Category?`, `account: Account?`, etc.) to the existing struct would either pollute every other call site OR break decoding for non-joined fetches. Instead a separate `TransactionListRow` struct decodes the joined query.
3. **No SwiftUI `TabView` introduction.** iOS already has `MainTabBar` (Phase 1) with 5 tabs; just swapped the `.transactions` case content from placeholder to `TransactionsView`.
4. **No new `AddTransactionFab` component.** iOS already has `FloatingActionButton` mounted on `AuthenticatedRootView`'s overlay (Phase 7). It opens `AddTransactionWizardView` — a working multi-step wizard. The prompt's instruction to ship a "stub FAB that no-ops" was based on a wrong assumption about iOS state. iOS already has a working wizard from Phase 7. Left untouched.
5. **`@Published` → `@Observable`** (Phase precedent). All new state uses `private(set) var` on the existing `@Observable` AppState.
6. **`Double` amounts → `Decimal`** (iOS convention). `Decimal` doesn't conform to PostgREST's `PostgrestFilterValue`, so the `.gte`/`.lte` filters convert via `NSDecimalNumber(decimal:).doubleValue`. The list itself stays Decimal; only filter values bridge to Double.
7. **`isArchived` on Category and Account → `archived`** (column name is just `archived` on these tables; iOS Goal model uses `is_archived` because that's a different table). The filter sheet excludes rows with `archived == true`.
8. **`is_active=true` filter on accounts** — skipped; the audit's blueprint wanted this but iOS doesn't model it consistently. The Account model has `archived` only.
9. **Currency formatting** — reused `CurrencyFormatter.format(_:code:)` from Phase 1 instead of inlining a `NumberFormatter`.
10. **Category emoji map** — reused the existing `IconResolver.resolve(_:)` (Lucide → emoji map already shipped in Phase 4 via `Sika/Core/Utilities/IconResolver.swift`) instead of inlining the prompt's small map. Wider coverage + single source of truth.
11. **Adjustment SF Symbol** — used `scalemass` (available in iOS 17.6) instead of the prompt's `scale.3d` (which is also SF Symbols but carries a different visual).
12. **`FlowLayout`** — already exists at `Features/Transactions/Components/Step1/FlowLayout.swift` (Phase 7). Reused.

## Behavioral notes

- **First load**: the orchestrator's `.task` only fires `loadFirstTransactionsPage()` if the list is empty. Tab switches don't refetch.
- **Filter change → refetch**: `.onChange(of: filters)` triggers `loadFirstTransactionsPage()` automatically.
- **Pull-to-refresh**: re-runs `loadFirstTransactionsPage()` (resets pagination).
- **Search**: client-side OR match across note / category name / account name / from_account name / exact absolute amount. Doesn't trigger refetch.
- **Bucket filter**: client-side; doesn't trigger refetch (matches web).
- **Delete flow**: 3-dot → Delete → SwiftUI `.alert` confirms with the transaction's display label + amount → on confirm, fires `deleteTransactionFromList`. Optimistic local removal animates the row exit; total count decrements.
- **Pagination**: 50 per page. "Load more" appears only when `transactionsList.count < totalCount`. Manual button (NOT infinite scroll).
- **Empty state**: "No transactions match your filters" + "Clear filters" link if any filter is active.
