## Divergences from the prompt

1. **`StreakService.markLoggingMilestoneShown` / `markSavingsMilestoneShown`
   not added.** The prompt asked for these. After reading
   `StreakEngine.updateLoggingStreak` / `updateSavingsStreak`, both already
   append the milestone to `streaks.{logging,savings}_milestones_shown` on
   the same call (lines 80–82 / 146–148). `StreakService.persist` then
   writes the updated row. Adding separate mark-shown methods would
   double-write. Behavior is equivalent: a milestone shows exactly once
   per user, gated by the engine.

2. **Edit entry uses the existing 3-dot Menu's Edit button, not a
   swipe-leading action.** The prompt sketched a `.swipeActions(edge:
   .leading)`. The pre-T2 `TransactionRowView` already shipped a Menu
   with an Edit placeholder (`print("📝 Edit tapped (T2 pending)")`).
   Hooking the existing button matches the dogfood expectation and is
   discoverable; a swipe-leading action can be added later if user testing
   prefers it.

3. **`AppState.replaceTransaction(_:)` doesn't touch `transactionsList`
   directly.** That list is `[TransactionListRow]` (joined), not
   `[Transaction]`, so a direct swap is incorrect. The wizard's edit
   path calls `refreshTransactionsListAfterSave()` instead — the server
   returns the fresh joined row.

4. **T1 list refresh is unconditional (still server-filter gated).**
   The prompt sketched a client-side `transactionMatchesCurrentFilters`
   check. That would need replicating the server's period/type/account/
   category/bucket/amount predicates correctly — easy to drift. Calling
   `loadFirstTransactionsPage()` defers the check to the server (which
   already runs that exact filter set). No-op when T1 isn't loaded yet.

   updates

3. Add transfer → "Transfer logged", +2 bubble

   unchanged

   DB has `paid_from_goal_id`

   toast, fires only once

   bubble, goal's `completed_at` populated
8. T1 filtered to current cycle → new row appears at top if it matches;
   filtered out otherwise
